# 文档优先开发

把仓库当作记录系统，而不是把关键知识留在对话里。每次开发开始前，先按统一结构完成或更新文档包，明确范围、设计、计划、验收和风险；用户审阅通过后，再修改项目代码。

## 不可跳过的闸门

在目标任务的文档包完成并且用户明确批准进入开发之前：

- 不得修改业务代码、测试实现、数据库结构、基础设施、依赖清单、生成代码或运行配置。
- 可以只读检查仓库、运行不会改变项目状态的命令、创建或更新 Markdown 文档。
- 如果用户直接要求写代码，也先完成必要文档并暂停。不要用“用户已经要求实现”代替审阅批准。
- 只有用户明确说明可以跳过本 skill 的文档审阅闸门时，才允许直接进入开发。
- 用户只要求写文档时，在文档完成后停止，不附带代码改动。

发生这些情况时，先向用户说明当前停在文档审阅阶段，并给出具体文档链接。

## 每次任务的工作流

1. **读取现状**
   - 先读仓库根目录的 `AGENTS.md`，再读 `ARCHITECTURE.md`。
   - 只读取与当前任务直接相关的 `docs/` 文档；不要默认加载整个目录。
   - 检查代码入口、包管理器、测试命令、关键模块和当前工作区状态。
   - 记录已有文档、缺失文档和可能过期的内容。

2. **判断文档增量**
   - 新项目或缺少文档基线：建立完整目录骨架，再填写与任务相关的真实内容。
   - 已有项目：保留用户文档和结构，只修改受当前任务影响的文件。
   - 每个任务都至少要在 `docs/PLANS.md` 留下目标、范围、验收和验证方式。
   - 中等或大型任务必须创建 `docs/exec-plans/active/<task-slug>.md`。

3. **编写中文文档包**
   - 写清目标、非目标、边界、子任务、验收标准、验证方式和依赖。
   - 涉及产品行为时更新产品规格；涉及架构时更新架构和设计文档。
   - 涉及前端、数据库、安全、可靠性时，同步更新对应专题文档。
   - 对不确定信息标记为“待确认”，不要编造事实。
   - 优先链接已有事实，避免在多个文件中复制同一段说明。

4. **做文档自检**
   - 检查链接、文件名、状态、任务归属和验收标准。
   - 检查 `AGENTS.md` 是否仍然只是短地图。
   - 检查执行计划是否包含可独立验证的子任务。
   - 检查文档中的命令和验证方式是否实际可执行。

5. **暂停并请求审阅**
   - 汇总创建和更新了哪些文档，以及关键决策和待确认项。
   - 明确请求用户批准进入开发。
   - 在本轮结束前不要开始代码实现。

6. **批准后实现**
   - 按已批准文档实现，保持改动范围一致。
   - 持续更新执行计划的进度、决策和验证结果。
   - 完成后把计划从 `docs/exec-plans/active/` 移到 `docs/exec-plans/completed/`。
   - 把评审意见、缺陷原因和新的工程约束回流到文档、测试、lint 或脚本。

## 标准文档结构

以这个结构为仓库文档基线：

```text
AGENTS.md
ARCHITECTURE.md
docs/
├── design-docs/
│   ├── index.md
│   ├── core-beliefs.md
│   └── ...
├── exec-plans/
│   ├── active/
│   ├── completed/
│   └── tech-debt-tracker.md
├── generated/
│   └── db-schema.md
├── product-specs/
│   ├── index.md
│   ├── new-user-onboarding.md
│   └── ...
├── references/
│   ├── design-system-reference-llms.txt
│   ├── nixpacks-llms.txt
│   ├── uv-llms.txt
│   └── ...
├── DESIGN.md
├── FRONTEND.md
├── PLANS.md
├── PRODUCT_SENSE.md
├── QUALITY_SCORE.md
├── RELIABILITY.md
└── SECURITY.md
```

`db-schema.md`、`new-user-onboarding.md` 和 references 下的文件是示例，不是所有项目都必须存在的内容文件。目录和根级文档是固定基线；专题内容按实际复杂度创建。

需要初始化骨架时运行：

```bash
python scripts/scaffold_repo_docs.py <repo-root>
```

脚本只创建缺失文件，不覆盖已有文档。随后必须把占位内容替换为项目事实，不能把空模板当作已完成文档。

## 文档路由

- 创建、审计或迁移仓库文档结构时，读取 [document-contract.md](references/document-contract.md)。
- 起草任一文档或执行计划时，读取 [document-templates.md](references/document-templates.md)，只使用当前任务需要的模板。
- 需要判断某类变更该更新哪些文档时，查阅 contract 中的更新触发表和任务分级表。

## 任务规模

| 规模 | 典型场景 | 最低文档动作 |
| --- | --- | --- |
| 小任务 | 单文件或少量文件的低风险修改 | 更新 `docs/PLANS.md`，写清目标、改动点、验收和验证 |
| 中等任务 | 多文件行为变化、需要测试策略或影响用户流程 | 创建精简执行计划，按需更新产品规格、前端或设计文档 |
| 大型任务 | 跨模块、数据模型、安全、可靠性或长期重构 | 创建完整执行计划，补齐架构、设计和专题文档，拆成可验证子任务 |
| 新项目 | 尚无文档基线 | 建立完整目录骨架，填写根文档和首个任务的执行计划 |

任务规模只决定文档深度，不取消“先文档、后审阅、再开发”的闸门。

## 文档写作规则

- 默认使用简洁中文 Markdown；已有英文文档为主时，先询问用户是否切换语言，不要擅自大规模翻译。
- 文件名使用小写短横线；保留 `AGENTS.md`、`ARCHITECTURE.md` 等约定文件名。
- `AGENTS.md` 是地图，不是百科全书；只放项目目标、关键约束、文档入口和验证命令。
- 每份重要文档标明状态：草稿、待审阅、已批准、执行中、已完成、待更新、过期或不适用。
- 计划必须写非目标，防止范围漂移。
- 生成型文档必须写清数据来源和重新生成命令。
- 架构边界、依赖方向、命名、日志和可靠性要求，尽量转化为 lint、测试或脚本，而不是只写在文档里。
- 文档超过合理长度时，拆成一个文件解决一个问题，并从索引链接。

## MCP 与外部依赖

开发前判断任务是否依赖无法从仓库获得的信息。若需要 GitHub、数据库、浏览器、Figma、云服务或可观测性 MCP：

- 在计划的“依赖与工具”部分写明推荐工具、解决的问题、替代方案和风险。
- 在进入开发前告知用户，并等待用户确认是否配置。
- 不要把计划建立在一个尚未确认可用的 MCP 上。

## 审阅闸门回复格式

文档准备完成后，用类似下面的结构回复并停止：

```text
我已经完成本次开发前的文档包，并暂停在代码开发前。

请你审阅：
- <文件>：<用途与关键决策>
- <文件>：<用途与关键决策>

待确认：
- <问题或假设>

如果你确认方向没问题，我再按这些文档开始实现，并在开发过程中同步更新执行计划。
```

不要只说“文档已准备好”。必须让用户能直接看到审阅对象、关键决策和需要拍板的事项。
