# 文档优先开发

让需求、设计、计划和验证结果保留在仓库中。先理解任务，再选择需要更新的文档，避免与已有规格形成两套事实来源。

## 上下文与文档布局

先读目标仓库的 `AGENTS.md`、`ARCHITECTURE.md`（如存在），再按任务读取相关规格、配置、代码与验证命令，检查工作区已有改动。

`docs/` 相对于目标仓库；`scripts/`、`references/` 相对于本 skill 目录。已有项目使用 `specs/` 或其他布局时保留它，通过入口链接建立导航，不要求复制或迁移全部文档。

## 按规模选择动作

| 规模 | 条件 | 文档动作 |
| --- | --- | --- |
| 轻量修改 | 局部、目标明确、低风险，如错字、简单样式或不改行为的整理 | 更新实际受影响的已有文档；必要的范围和验证可写在回复或已有任务记录，不强制创建计划或完整骨架 |
| 普通功能 | 多文件行为变化或独立用户流程 | 保留需求/AC、设计、任务和验证；使用已有规格，或在 `docs/PLANS.md` 记录计划并链接相关文档 |
| 重大变更 | 架构、数据迁移、权限、兼容性或重要外部契约变化 | 创建执行计划，明确影响、验收、风险与回滚，按需更新架构及专题文档 |
| 建立文档体系 | 用户要求初始化或补齐文档基线 | 创建当前项目需要的入口和文档；只有确实需要完整基线时才运行骨架脚本 |

用户明确要求严格的“先文档、审阅通过后开发”时，按该模式执行；其他任务依据已有授权和实际待决事项推进。

## 审阅与授权

- 用户要求先审阅、目标仓库有明确审阅规则，或存在影响行为、范围与兼容性的未定关键决策时，先准备具体可审阅文档，链接关键决策，再请求所需确认。
- 同一任务范围内的已有批准持续有效。用户已要求按确认方案实现时继续执行，不因重新加载 skill 或切换阶段重复审批。
- 用户明确要求跳过或调整文档流程时，尊重其选择并保留必要的范围、验收及验证记录。
- 只要求文档时完成文档后停止；要求实现时，在必要决策明确后继续开发。提交、推送、部署或其他外部动作仍需在各自授权范围内执行。

## 工作流

1. 根据任务规模确定需要更新的文档和可验证目标；复用已有事实，未知项标为待确认，区分阻塞项与不影响执行的假设。
2. 写清目标、范围、验收、实现思路和验证方式；普通或重大变更按需要记录非目标、依赖、风险、回滚和子任务。
3. 检查路径、链接、状态及命令是否匹配仓库。只在触发上述审阅条件时暂停；其他情况继续已授权工作。
4. 实现期间更新受影响文档和计划中的进度、决策、验证结果。范围变化时只确认新增且需要用户决定的部分。
5. 仅在实现和必要验证通过后标为完成；有活动执行计划时，将其移到完成目录并更新索引链接，保留未验证项。

## 文档结构和参考

新项目的常用导航是 `AGENTS.md`、`ARCHITECTURE.md`、计划入口以及产品规格和设计文档。前端、安全、可靠性、质量等专题按实际需求创建。

- 建立、审计或迁移文档体系时，读取 [document-contract.md](references/document-contract.md)。
- 起草文档或执行计划时，按需读取 [document-templates.md](references/document-templates.md)，只使用需要的模板。
- `AGENTS.md` 保持简短，导航到现有规格；文件名沿用仓库约定，内容语言默认与项目一致。
- 生成文档记录来源和生成命令；不要把空模板当成完成的规格或获得批准的计划。

需要完整骨架时，在本 skill 目录运行，或将脚本路径替换为其绝对路径：

```sh
python scripts/scaffold_repo_docs.py <repo-root> --dry-run
python scripts/scaffold_repo_docs.py <repo-root>
```

可用 `--task-title "新增评论"` 创建任务计划，默认文件名支持中文；也可传 `--task-slug add-comments`。已有同名同标题计划原样保留，文件名与另一任务冲突时失败并提示另选 slug。`--dry-run` 不写文件。生成后需填写项目事实。

## 外部工具与交付

先检查任务需要的工具是否已可用。MCP、CLI、项目脚本或直接测试能完成同等目标时选择实际可用的办法；只有缺少关键能力且无法替代时，说明阻塞和用户需要补充的配置。

最终提供文档链接、关键决定、实现与验证结果、仍待确认或未验证的事项。需要审阅时让用户能直接检查具体对象；已获授权时继续完成相应任务。
