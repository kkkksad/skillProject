# 仓库文档契约

这份参考定义每个文档的职责、更新触发条件和验收方式。只读取当前任务需要的部分。

主要依据：OpenAI《Harness engineering: leveraging Codex in an agent-first world》
<https://openai.com/zh-Hans-CN/index/harness-engineering/>。

## 核心原则

- 仓库是事实来源：产品、架构、计划、质量和运维知识必须版本化。
- `AGENTS.md` 是地图：保持简短，只导航到更深的事实来源。
- 渐进披露：先读短入口，再按任务读取相关文档。
- 文档可执行：命令、路径、链接、状态和重新生成方式必须能验证。
- 不变量优先：能由测试、lint 或脚本强制的规则，不只写在文档里。
- 反馈回流：评审意见、缺陷和重构经验要变成文档更新或自动检查。

## 根级文档

### `AGENTS.md`

职责：给 Codex 和其他 agent 的短导航。

必须包含：

- 项目目标和目标用户，2-4 行。
- 主要技术栈、运行入口和关键目录。
- 架构、产品、计划、质量和安全文档的入口。
- 安装、测试、lint、构建和验证命令。
- 每次任务都必须遵守的关键约束。
- 文档更新和审阅闸门规则。

更新触发：仓库结构、验证命令、文档入口或关键约束变化。

不要包含：完整架构说明、长篇教程、重复的业务背景、容易过期的细节。

### `ARCHITECTURE.md`

职责：系统级事实地图。

必须包含：

- 主要业务域、模块和运行时边界。
- 数据归属和关键依赖方向。
- 外部集成、异步流程和关键基础设施。
- 架构不变量及其强制方式。
- 已知风险和待治理项。

更新触发：模块边界、依赖方向、数据归属、运行时或外部集成变化。

## `docs/` 目录

### `docs/design-docs/`

用途：记录需要长期保留的技术设计、取舍和工程判断。

`index.md` 至少列出文档名称、状态、负责人或归属、最后验证日期。`core-beliefs.md` 记录团队稳定认可的工程原则。

更新触发：跨模块设计、重要技术取舍、容易被重新争论的决策、长期约束。

### `docs/exec-plans/`

`active/` 保存执行中的计划，`completed/` 保存完成后的历史记录，`tech-debt-tracker.md` 管理已知延期事项。

执行计划至少包含：

- 状态和任务负责人
- 目标
- 范围与非目标
- 子任务及各自验收标准
- 涉及文件和模块
- 依赖与工具
- 风险与回滚
- 验证方式
- 进度记录
- 决策记录
- 完成后需要更新的文档

更新触发：中等或大型任务的每次实施、验证、范围变化和完成。

### `docs/generated/`

用途：保存从代码、数据库或配置生成的文档，例如 schema、路由和依赖图。

每份生成文档必须写：

- 数据来源
- 生成命令
- 生成时间或版本
- 是否允许手工修改

更新触发：数据源或生成方式变化。不要手工维护可由机器稳定生成的内容。

### `docs/product-specs/`

用途：记录用户可见行为、产品决策和验收标准。

产品规格建议包含：

- 用户问题
- 目标用户
- 核心流程
- 边界和失败状态
- 权限或数据约束
- 验收标准
- 成功指标或观测信号

更新触发：新增或改变用户流程、权限、文案语义、数据展示和业务规则。

### `docs/references/`

用途：保存 agent 在特定任务中需要读取的内部或外部参考资料，例如设计系统摘要、框架约束、API 说明和部署要求。

更新触发：引用上游资料变化，或反复需要从外部重新收集同一信息。

不要复制整本手册。优先记录来源、适用版本、关键约束和更新方式。

### `docs/DESIGN.md`

用途：记录视觉和交互设计的不变量。

包括：设计原则、布局、排版、颜色、间距、组件规则、交互反馈、无障碍和响应式要求。

更新触发：视觉规范、设计 token、核心组件或交互模式变化。

### `docs/FRONTEND.md`

用途：记录前端实现边界。

包括：路由、状态管理、数据获取、组件组织、表单、错误状态、可访问性、浏览器验证和性能约束。

更新触发：前端架构、路由、状态模型、关键组件或验证方式变化。

### `docs/PLANS.md`

用途：轻量计划入口和活跃执行计划索引。

每个任务至少记录：

- 任务名称和状态
- 目标
- 改动范围
- 验收标准
- 验证方式
- 执行计划链接，如果有

更新触发：每个开发任务开始时，以及在完成、暂停或取消时。

### `docs/PRODUCT_SENSE.md`

用途：记录产品判断标准。

包括：目标用户、核心问题、优先级原则、取舍标准、体验底线和“做得好”的定义。

更新触发：目标用户、产品策略、优先级或体验标准变化。

### `docs/QUALITY_SCORE.md`

用途：定义质量和完成度。

包括：文档质量、实现质量、测试覆盖、可访问性、性能、可维护性、已知缺口和可自动检查项。

更新触发：质量门槛、检查方式或重大缺口变化。

### `docs/RELIABILITY.md`

用途：记录可靠性和运行准备度。

包括：失败模式、超时、重试、降级、幂等、迁移、监控、告警和恢复步骤。

更新触发：运行路径、外部依赖、故障处理或部署方式变化。

### `docs/SECURITY.md`

用途：记录安全和数据边界。

包括：认证、授权、密钥管理、敏感数据、输入验证、审计、威胁模型和安全审查要求。

更新触发：权限、数据流、外部集成、密钥或攻击面变化。

## 更新触发矩阵

| 变更类型 | 至少更新 |
| --- | --- |
| 任意代码变更 | `docs/PLANS.md` |
| 中等或大型任务 | `docs/exec-plans/active/<task>.md` |
| 用户可见行为 | `docs/product-specs/` |
| 跨模块或边界变化 | `ARCHITECTURE.md`、`docs/design-docs/` |
| 前端或交互变化 | `docs/FRONTEND.md`、`docs/DESIGN.md` |
| 数据库或 API 结构 | `docs/generated/`、`ARCHITECTURE.md` |
| 权限、数据处理或密钥 | `docs/SECURITY.md` |
| 部署、故障处理或可观测性 | `docs/RELIABILITY.md` |
| 验证命令或入口变化 | `AGENTS.md` |
| 产品优先级或判断标准 | `docs/PRODUCT_SENSE.md` |
| 质量门槛或已知缺口 | `docs/QUALITY_SCORE.md` |
| 长期延期事项 | `docs/exec-plans/tech-debt-tracker.md` |

## 状态规则

使用以下状态之一：

- `草稿`：内容仍在形成，不能作为开发依据。
- `待审阅`：文档包完整，等待用户批准。
- `已批准`：用户允许按此文档进入开发。
- `执行中`：实现正在进行。
- `已完成`：实现和验证均完成。
- `待更新`：相关事实已变化，需要同步。
- `过期`：文档与现状冲突，不能继续依赖。
- `不适用`：项目明确不需要该文档，并写明原因。

审阅闸门只接受“已批准”。文档存在不等于进入开发获得批准。

## 建立或迁移文档基线

1. 先检查已有 `AGENTS.md`、`ARCHITECTURE.md` 和 `docs/`，不要覆盖用户内容。
2. 新项目运行 `scripts/scaffold_repo_docs.py <repo-root>` 建立缺失骨架。
3. 用仓库事实替换占位内容；无法确认的事项标为“待确认”。
4. 迁移已有项目时，优先建立索引并补充链接，再逐步迁移长文档。
5. 不要为了结构完整而复制通用教程或制造空壳文档。

## 文档验收清单

- `AGENTS.md` 能在很短时间内说明项目入口和文档地图。
- 当前任务在 `docs/PLANS.md` 中有记录。
- 中等或大型任务有独立执行计划。
- 计划包含目标、非目标、子任务、验收和验证。
- 所有相对链接都能解析。
- 重要文档有明确状态。
- 生成型文档有重新生成命令。
- 文档中的事实与代码、配置和命令一致。
- 不变量已有自动检查，或明确记录尚未自动化的风险。
- 待确认项已集中列出，没有被伪装成确定事实。
