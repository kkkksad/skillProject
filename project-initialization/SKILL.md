# 项目初始化

按项目规格创建或补齐工程骨架，保留已有内容，不自行变更已确定的技术栈。

## 上下文与路径

先读目标仓库的 `AGENTS.md`、工程配置和相关规格（如存在）。默认输入是 `specs/技术栈.md`、`specs/项目结构.md`、`specs/开发规范.md`；已有项目采用其他路径时记录映射并沿用。`assets/` 相对于本 skill，其他路径相对于目标项目。

`specs/PROJECT-CONTEXT.md`、`specs/GUARDRAILS.md` 是可选补充，缺失不阻止执行。新项目需要明确技术栈、入口和基本结构；这些信息可以来自文档或用户已确认的描述，只有影响结果的未知决策需要补问。

## 先判断实际状态

| 状态 | 判断依据 | 动作 |
| --- | --- | --- |
| 只有文档或 Git | 尚无对应技术栈的工程配置和源码入口；`.git` 可以是目录或 worktree 文件 | 初始化工程，保留已有文档和 Git 状态 |
| 部分骨架 | 部分配置、入口或规划目录已存在 | 对照规格列出缺失项，只补齐必要内容 |
| 骨架齐全 | 配置、入口及必要目录均存在 | 不重复运行脚手架，执行可用的安装、启动或构建检查 |

不要仅凭 `.git`、某个目录或单个 `package.json` 判定初始化完成。检查当前目录及上级 Git 仓库，已在仓库内时无需再次 `git init`。

## 执行

1. 检查工作区已有改动、核心工具版本和目标目录，列出准备创建的内容。
2. 依据技术栈选择实际脚手架命令，不把通用的 `npm init` 当成所有框架的完整初始化。先确认命令在含有规格文档的非空目录中如何工作；必要时在临时目录生成后，仅复制目标缺失的文件。
3. 依据实际框架结构创建目录和配置。使用当前 shell 支持的命令；只给确实需要纳入 Git 的空目录添加 `.gitkeep`，不对依赖、构建输出或缓存目录添加。
4. 按需生成 `.gitignore`、启动说明和 `.env.example`，示例中不写真实密钥。已有文件先读取，再做授权范围内的增量更新；需要覆盖用户内容时先展示具体差异。
5. 执行适用的启动、构建、类型检查或配置检查，区分成功、失败与环境阻塞。失败时保留可诊断结果，不能仅因文件已生成就报告完成。

全栈项目同时核实前后端入口、必要服务及本地环境配置；按实际栈提供迁移/测试数据命令、测试入口和最小 CI 检查。先打通可运行骨架，不提前实现全部认证或业务模块。只有用户要求容器化或部署配置时才添加相应产物，不强制 Docker。测试数据库和密钥与生产隔离。

## 记录与交付

使用 `assets/initialization-log-template.md`，保存到 `docs/开发记录/初始化记录.md`；已有记录追加本次运行，保留历史。即使无需补齐骨架，也可以记录检查结果，不再声称完全没有文件修改。

汇报创建、补齐或跳过了哪些内容、执行命令及结果、尚未验证的入口。用户只要求初始化时到此结束；明确要求继续开发时沿用已确认信息推进。提交、推送或发布需在用户授权范围内执行。
