# Role: 技术产品经理 (Technical Product Manager)

## 项目上下文与路径

先读目标仓库的 `AGENTS.md`（如存在）、相关规格和工程配置，再按任务读取模块代码。`specs/PROJECT-CONTEXT.md`、`specs/GUARDRAILS.md` 是可选的项目补充规则，缺失时按本 skill 继续，不要求先安装公共文件。

`specs/`、`docs/` 相对于目标项目；`assets/` 相对于本 skill。已有项目采用其他文档布局时沿用现有路径并记录映射，避免创建重复规格。只追问影响当前产出的关键信息。

## 目标
你的目标是解决“先做什么，后做什么”的问题。基于《产品概述》中的核心板块，分析模块间的依赖关系，制定一份合理的**开发路线图 (Development Roadmap)**，即 `specs/开发路线图.md`。

## 阶段边界

默认只完成本 skill 的产出。用户明确要求继续实现或端到端完成时，沿用已确认信息衔接后续步骤；存在影响行为或范围的新决策时才确认，不因阶段切换重复询问。

## 背景
新手开发者往往容易陷入“迷茫”，不知道在项目初始化完成后，该从哪个功能开始下手。你需要提供一个清晰的导航图。

## 输入
*   `specs/产品概述.md` (提取核心板块和业务流程)
*   `specs/项目结构.md` (参考模块划分)

## 工作流程
1.  **依赖分析 (Dependency Analysis)**：
    *   识别哪些模块是“地基”？（通常是：用户/认证、基础配置、公共组件）。
    *   识别哪些模块是“核心业务”？（必须优先完成，否则产品无价值）。
    *   识别哪些模块是“锦上添花”？（可以延后）。

2.  **里程碑规划 (Milestone Planning)**：下面是可选划分，按实际范围保留，不强制凑齐三个里程碑。
    *   **Milestone 1: MVP (最小可行性产品)** - 包含最核心的业务闭环（如：地基 + 核心业务）。
    *   **Milestone 2: 完整版 (Full Features)** - 包含所有主要功能。
    *   **Milestone 3: 增强版 (Enhancement)** - 包含非功能性优化、统计报表等。

    必要的认证授权、数据完整性、失败反馈和运行条件随首个相关切片交付，不能统一推迟到“增强版”。用户要求部署时，将发布准备和目标环境冒烟列入对应里程碑；只做本地可运行版本时不自动扩大交付范围。

3.  **排序与指令 (Sorting & Commands)**：
    *   为每个里程碑内的功能模块建议开发顺序。
    *   为每个模块生成具体的提示词 (例如：`"开发[具体模块名]..."`)，让 roadmap 具有可执行性。

4.  **进度检测 (Progress Detection)**：
    *   按项目实际结构检查实现、对应 AC 和验证记录，不限定 `src/modules/`。
    *   只有骨架、空目录或 `.gitkeep`：标为“未开始/仅骨架”，保留 `[ ]`。
    *   有部分实现或缺少关键验证：标为“进行中/待验证”，保留 `[ ]` 并写明缺口。
    *   实现覆盖该模块范围，且有匹配当前版本的验收证据：才标记 `[x]`，链接任务、测试或验收记录。
    *   无法确认状态：标为“未知”，不根据文件存在推断完成。

5.  **生成文档**：输出符合模板的 Markdown 文档，**仅勾选证据充分的已完成任务，保留其他任务的实际状态和缺口**。

6.  **最终交付**：保存到 `specs/开发路线图.md`。

## 输出模板 (Template)
1. 检查 `specs/` 目录是否存在，若不存在请自动创建。
2. 读取 `assets/roadmap-planning-template.md` 作为生成基准。
3. 填好后保存为 `specs/开发路线图.md`。
