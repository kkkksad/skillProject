# 全栈项目流程

负责选择入口、衔接阶段和核对交付边界；各阶段的详细方法交给对应技能。支持全栈框架、前后端分离或托管后端，不预设语言、框架、数据库或部署平台。

## 先确定起点与终点

1. 读取目标项目的 `AGENTS.md`、根说明、工程配置和工作区状态，再按当前任务读取规格、代码与测试。已有目录和文档沿用，不迁移出另一套事实来源。
2. 从用户请求确定终点：讨论/规划、可运行功能、发布准备或部署到指定环境。明确要求做完整项目时完成当前约定范围的实现与验收；未约定远端发布时不自动部署。
3. 核实已有能力和验收证据，选择尚未满足的阶段。已有栈、需求和授权直接复用；只有影响范围、产品行为、预算、数据边界或兼容性的未定决策需要确认，先形成可审阅方案。

## 选择路径

| 当前情况 | 阶段与交接 |
| --- | --- |
| 从想法启动新项目 | project-requirements-clarification → project-product-overview → project-tech-stack → project-structure / project-dev-standards → project-roadmap-planning → project-initialization |
| 新增业务功能 | feature-requirements-clarification（信息不足时）→ feature-tech-design → feature-task-planning → feature-implementation |
| 调整已有功能 | feature-evolution 评估影响并补增量任务 → feature-implementation；局部明确的小改动直接实现并验证 |
| 既定行为出现缺陷 | bugfix-workflow；修复中发现产品行为未定时只澄清该部分 |
| 发布准备或部署 | project-release；准备完成后仅在实际发布已获授权且环境明确时部署 |
| 用户要求文档体系或仓库采用文档优先 | doc-first-development 管文档入口、状态和导航，链接已有规格；它不替代各阶段的业务设计 |

表中完整链路按已约定终点截取：只要求选型或方案时，交付对应文档后停止；不因从新项目开始就执行初始化和编码。

读取并应用本阶段技能后再执行；不一次加载全部技能和模板。某个技能未安装时，按表中职责完成等价工作并说明缺口，不能声称已经调用。Steiner Archive 等仓库专用技能只在匹配仓库使用，不属于必经阶段。

## 推进与记录

- 新项目先交付一条最小业务闭环，再逐步扩展；按用户可观察行为做垂直切片。用户操作顺序不自动成为开发依赖，已有数据和接口可以独立复用。
- 轻量修改只记录必要范围与验证；普通功能保留 AC → 设计 → 任务 → 验证的追溯，可合并在现有文档；重大变更补兼容、迁移、风险与恢复方案。不强制每个阶段单独生成文件。
- 默认新项目规格在目标仓库 `specs/`，过程证据在 `docs/`；已有项目记录实际路径映射。阶段交接只携带当前范围、已有决策、输入/产出路径、验收方式、未决项和下一步，可使用已有任务记录承载。
- 同时存在其他流程技能时，按职责组合：需求讨论复用现有结论；文档技能负责导航；设计/任务技能负责各自产出；TDD 和调试方法用于实现；发布技能负责环境交付。单一事实来源、一次确认覆盖同一授权范围，不重复建计划或验收报告。
- 中途需求变化时更新受影响 AC 和任务；保留不受影响的实现及历史证据，仅对本次变化需要的新决定补问。

## 完成判定

对照用户约定的终点检查证据：功能需通过相关测试及适用的页面、接口、权限和数据链路验证；发布需有目标环境的版本及冒烟结果。mock 单测不能证明真实接口可用，本地通过不能证明远端部署成功。

关键验证无法执行时记录环境、缺口与下一步，标记待验证；可继续处理的独立任务继续推进。最终汇报已交付范围、证据链接、已知限制和发布状态，完成标签与实际证据一致。
