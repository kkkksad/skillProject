# 知识文章

## 位置与模板

从 `templates/article.md` 开始，按记录用途放入 `content/` 的对应分类。不要自行创建与现有信息架构冲突的新目录；先查看同类记录的分类和链接方式。

站点自动生成一级标题，正文从二级标题开始。默认使用 Markdown；只有确实需要交互内容时才使用 MDX。

## 最小维护信息

frontmatter 至少应表达这些字段，实际名称和约束以仓库模板及类型定义为准：

| 字段 | 含义 |
| --- | --- |
| `title` | 文章标题 |
| `description` | 一句话说明适用问题 |
| `owner` | 维护人或团队 |
| `status` | `draft`、`reviewed` 或 `deprecated` |
| `lastVerified` | 最近核验日期，格式 `YYYY-MM-DD` |
| `appliesTo` | 适用项目、工具版本或环境 |

状态含义：

- `draft`：新方案、待确认结论，或证据尚未补齐。
- `reviewed`：已在对应场景验证并完成审查。
- `deprecated`：不再建议采用，但必须保留历史原因和替代入口。

## 正文结构

按实际内容写清以下部分，不必机械保留空标题：

- **场景**：具体触发条件、症状和预期。
- **约束**：业务语义、运行环境、版本和适用边界。
- **方案**：选择的办法以及选择依据。
- **证据**：复现方式、测试结果或现场观测。
- **关联**：ADR、源代码、相关记录和官方资料。

被放弃的方案说明放弃原因，方便后来者重新评估。只写可复用的事实和判断依据，避免复制大段无关资料。

## 修订与弃用

- 发现错误时做小范围修正，并检查引用该记录的页面。
- 环境、版本或适用范围变化时重新执行验证，再更新 `lastVerified`。
- 弃用记录时标记 `deprecated`，写清弃用原因和替代入口，不要直接删除可追溯的历史。
